# 连续任务模式：有界上下文与全新执行会话轮换

日期：2026-10-27。状态：**计划草案，未实现、未启用**。

本文记录用户批准编制的开发方案，不是当前运行契约。本轮只写计划，不改变模型配置、不启动自动任务、不重启或部署桌面/服务器。未来正式契约按仓库约定进入 `specs/v2/`，实施任务可迁移到 GitHub issues；本文不冒充已有 API 或配置文档。

## 1. 用户目标与已确认边界

用户希望长时间按开发计划连续工作，不必反复新开窗口并输入“继续”；不希望历史摘要、保留聊天和上下文在连续压缩中不断累积。

采用 **一个持久任务 + 多个顺序执行的全新会话**：任务长期存在，执行会话达到预算后更换；新会话读取项目计划、最新检查点及必要代码，不继承旧会话历史。旧会话保留用于审计，不删除、不清空、不 fork 搬运旧消息。

用户说明当前 Midea 接口支持 1M tokens。500K 是用户选择的任务模式预算，不是服务端能力上限，也不是要求全局下调所有会话或其他模型的限制。实际能力与可用预算在实现前核验。

已确认要求：

- 每轮上下文预算为 **500,000 tokens**。
- 接近预算时主动交接，而不是等到服务端拒绝或反复压缩后继续积累。
- 新轮启动输入上下文 **不超过 50,000 tokens**，不是仅把最近聊天保留量设成 50K。
- 保存任务状态后自动开始下一轮，直至完成、用户暂停、需要授权或出现不能自行解决的阻塞。
- 计划、代码与验证记录作为长期依据；不依赖完整历史聊天，也不假定有计划就可以省略实际代码核对。
- 用户界面呈现同一个任务及其轮次，不反复弹新窗口。

“轮”在本文指任务执行批次，**不等于一个 LLM step 或仓库保留的 assistant-turn 概念**。

## 2. 现有能力与缺口

已查阅 OpenCode V2 官方 [Session API](https://opencode.ai/v2/docs/api)、[Plugin API](https://opencode.ai/v2/docs/build/plugins) 和 [Compaction](https://opencode.ai/v2/docs/compaction)，并核对本仓库：

| 现有入口                                                            | 可复用边界                                                                                    |
| ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `specs/v2/session.md`                                               | 持久输入先于执行；Session ID 重用、控制输入、安全 step 边界与恢复语义                         |
| `packages/core/src/session/execution.ts`                            | 进程级 Session 执行协调、interrupt、awaitIdle、执行声明与恢复；旧执行停止不等于其副作用已撤销 |
| `packages/core/src/session/runner/`                                 | 按 step 重载历史、组装请求、执行工具；不是独立的内存 tool loop                                |
| `packages/core/src/session/compaction.ts`                           | 现有滚动摘要/近期历史压缩；不等于新会话轮换                                                   |
| `packages/schema/src/config/compaction.ts`                          | 现有 auto/keep/buffer；没有任务轮换或启动上下文总上限配置                                     |
| `packages/core/src/session/usage.ts`                                | 用量记录与计费；不能把任务累计输入用量当当前上下文大小                                        |
| `packages/core/src/util/token.ts`                                   | 当前文本估算为字符数除以 4；不能据此宣称精确的服务端 50K 硬上限                               |
| `packages/server/src/handlers/session.ts`、`packages/protocol/src/` | 现有会话操作及公开协议；精确类型须在实现时重新核验                                            |

缺口是任务级调度、持久交接、请求预算仲裁、任务级停止和界面，而不是再改一次 `compaction.keep.tokens`。

## 3. 方案选择与范围

建议正式实现放在 OpenCode Core/Server 的任务层，App/桌面显示任务状态；可先用现有 API 验证概念，但原型不能宣称具备可靠恢复和严格预算门槛。

任务调度器是普通程序状态机，**不另开一个持续积累上下文的主管 AI**。每个任务同时最多一个执行会话；首版限定当前本机服务器，不扩展集群调度或跨机器所有权。

首版包含：

1. 显式开始、暂停、继续和停止任务。
2. 按预算和已完成工作包交接到新会话。
3. 持久任务状态、可核验检查点、轮次记录与有限恢复。
4. 按同一任务查看当前轮、历史轮、阻塞和测试证据。
5. 已批准范围内自动继续；权限请求和用户决定保持显式。

首版不包含删除会话历史、自动提交/推送、任意项目无人值守授权、真实工业设备写入授权、集群 exactly-once、关机期间执行或无上限重试。Modbus只是验收用例，不把任务调度逻辑放进 VC 插件。

## 4. 预算规则

### 4.1 目标值

| 项目             | 目标     | 口径                                                                       |
| ---------------- | -------- | -------------------------------------------------------------------------- |
| 每轮上下文总预算 | 500,000  | 请求输入加预留输出空间；不得超出实际模型的 context/input 限制              |
| 主动交接起点     | 450,000  | 建议的初值，不是用户已指定的精确阈值；实现验证后可调整，确保检查点有余量   |
| 新轮启动输入上限 | 50,000   | 系统/项目指令、工具定义、任务输入、必要文件内容和交接信息合计              |
| 交接文字         | 小而有界 | 优先路径、工作包ID、事实和证据引用；具体子预算在P0冻结，不累计拼接前轮摘要 |

实际轮预算取用户目标和模型可用限制的较小值，预留输出与交接空间。预算由任务模式单独管理，不默认改动全局 provider/model 配置。

50K是防止启动上下文膨胀的**上限，不是必须填满的目标**。新轮只装载必要规则、工具与接续信息，具体代码在工作中按需读取。交接文字宜只有几千tokens量级，但不得把交接包大小当成完整启动输入大小；实际固定指令/工具开销与计量误差在P0测量后再冻结子预算。相对于500K轮预算，50K是合理的初始护栏，不代表未经实测就保证所有项目都能满足，也不要求为了凑到50K多加载历史或全文计划。

### 4.2 计量与硬上限资格

- 在每个模型请求发送前评估**本次完整输入**，不是按聊天条数或累计消费 tokens 触发。
- 缓存读取的内容仍属于输入上下文；不能忽略 cache，也不能把同一输入重复计入。
- 计入系统指令、工具 schema、文本、图片等附件和 provider 特有内容；后置 hook/body overlay 等实际请求变更也必须覆盖，不能只测编辑前的用户文本。
- provider 返回的完整输入用量用于校准与审计，但它发生在发送后，不能单独作为发送前硬上限保证。
- 明确区分估算值与 provider 实测值。只有 tokenizer/协议计量具备可验证的上界时，才能宣称严格的50K发送前门槛；字符数/4只足以做原型，不是硬上限证明。
- 计量不具备保证或固定指令/工具本身超过50K时，严格模式应拒绝启动并给出原因。不能通过丢弃系统指令、权限规则或安全约束来“达标”。按任务选择工具/按需读取内容可以优化，但不得私自减弱规则。
- 50K是**新轮启动**门槛，不是整个执行过程永远只能用50K。后续按需读取代码、运行工具后上下文可以增长，接近轮预算时再次交接。
- 大工具返回可能跨过主动阈值，必须在下一次模型发送前重新检查。没有足够交接余量时暂停并保留实际状态，不把超预算请求照常发送。

## 5. 持久任务与检查点

### 5.1 任务级状态

建议任务具有独立身份，关联项目/Location、计划入口、验收标准、用户批准范围、预算策略及执行轮记录。每轮关联全新Session ID和检查点版本。

持久事实只记录不可从既有历史推导的变化；当前状态、活动会话和轮次清单由投影获得。不要为任务再复制整份Session日志，Schema/Core/Protocol/Server依赖方向遵守根AGENTS规则。字段/API名称与持久事件设计在实施阶段评审，不在本文假装已有类型。

用户已批准的任务范围可以延续，但一次性设备写许可、临时授权或旧会话工具审批不得因轮换自动变成永久权限。

### 5.2 检查点内容

每轮完成或交接前，应更新项目计划与必要验证报告，并形成小型任务检查点：

- 本轮完成的工作包、实际结果和仍未达到的验收条件。
- 精确下一项工作及停止/阻塞原因，不只是“继续”。
- 相关文件、测试命令、结果与证据路径；报告是否对应当前源码。
- 工作目录、源码基线、未提交改动说明；已有用户工作不能当作可清理的残留。
- 未完成工具/后台进程和不确定副作用；必要的复核步骤。
- 仍有效的用户要求和授权范围，禁止行动与待用户确认项。

计划是工作依据；检查点是接续线索。新会话仍要核对实际文件、机器状态和工作树，不能把模型写出的摘要当作已验证事实。日志/文档不因写进检查点就获得更高指令权限。

## 6. 执行与轮换流程

建议任务状态包括：待运行、运行、交接、暂停、等待用户、完成、失败。名称为设计草案，非已有公开枚举。

```text
用户开始任务
    → 保存任务范围、计划与验收标准
    → 创建全新执行会话
    → 检查启动输入预算
    → 持久提交接续输入并启动执行
    → 按计划开发/测试
        → 未到预算、未阻塞：继续当前轮
        → 达到主动阈值：进入交接
        → 已完成工作包但任务未完成：按状态继续，不等用户说“继续”
        → 需要权限/决定：等待用户
        → 验收达到任务终点：完成

交接
    → 禁止旧轮再启动新的普通工作
    → 在安全step边界落盘计划、报告和检查点
    → 确认旧执行及相关写入工具已结束
    → 保存本轮完成与下一轮关联事实
    → 创建全新会话，不复制历史
    → 校验新轮启动输入≤50K
    → 持久提交下一项并启动新轮
```

### 6.1 所有权与恢复

- 不能在工具写文件或外部命令仍运行时直接创建第二个写入者。等待旧会话idle只是必要条件，还要核对仍存活的后台任务；不能为了轮换强杀任意进程。
- 交接请求应在现有step/执行协调边界处理，不能从模型请求hook里随意重入Session执行或另建内存工具循环。
- 检查点失败或不完整时，不开始新轮；保留旧记录并暂停/有限重试。
- 创建下一轮和提交输入的重试应复用已保存身份并遵守现有首次输入获胜语义，不能因重复事件生成多个会话或重复任务输入。
- 任务控制意图先持久化，执行调度后进行；复用Session原有协调和恢复，不引入两个互相竞争的Session恢复者。
- 服务器重启后先对照任务交接阶段、既有Session claim和实际工具状态，再决定恢复哪一轮。未知外部副作用只要求核验，不自动重放。
- 用户暂停/停止必须阻止下一轮启动；普通“会话idle”、step用尽或生成一段最终回答，不自动判定整个任务完成，也不能用无穷“继续”消息绕过step/费用限制。
- 任务运行中新增用户输入要持久归属任务并保留顺序/取消语义。交接期间不能丢到已结束的旧会话、静默漏掉或同时重复送给两轮。

### 6.2 与普通压缩的关系

普通会话的自动/手动压缩保持原行为。任务模式预算轮换不能悄悄退化为无限滚动摘要；其请求仲裁要先于自动压缩，并说明手动压缩/模型切换与任务控制的交互规则。

达到任务阈值时采用全新会话，旧provider continuation/checkpoint不进入新轮。用户显式选择其他策略需单独记录；预算或计量失败不得静默改变模式。

## 7. 用户界面与停止条件

同一任务页展示：任务目标、计划入口、当前工作包、状态、当前轮、上下文估算/实测标识、轮换原因、最新检查点、测试证据、等待决定。展开历史轮可查看原会话，不自动开多个窗口。

控制入口：开始、暂停、继续、停止、查看检查点/历史轮。停止整个任务时，旧执行和待启动新轮都受控；界面区分“正在停止”与“已停止”，不能只取消当前流后又自动续跑。

下列情况停止自动推进并给出明确原因：

- 用户停止/暂停，或需要用户流程验收/关键技术选择。
- 权限拒绝、授权范围不足、设备/部署等需要显式审批。
- 相同失败或无进展连续达到已配置上限。
- 任务总费用、总时间或轮次达到用户设置的上限。
- 检查点、预算计量或新轮启动无法完成。
- 完成标准满足；不能仅凭模型说“完成”忽略未通过的验收项。

默认不自动批准新权限；不无限重试，不伪造完成率。人工停止不因进程重启被当成故障恢复而自动继续。

## 9. 必需验收场景

1. **预算边界**：阈值前/达到/跨过、大工具结果、输出预留、模型限制降低、缓存输入、非文本附件和hook请求变更；累计用量不触发错误轮换。
2. **新轮独立性**：旧用户/assistant消息、旧滚动摘要及provider continuation都不携带；仅加载必要指令与受限任务输入。超50K拒绝并说明，不静默丢安全规则。
3. **真实接续**：至少连续多个新会话完成同一计划中的不同工作包；更新证据并自动进入下一项，不用人手发送继续。
4. **串行写入**：工具仍在写、后台命令未结束、交接中断时没有第二个写入者；已有未提交用户改动保持不动。
5. **故障恢复**：分别在检查点前后、旧执行结束后、下一会话创建后和输入提交后中断服务器；恢复采用已保存身份，不重复创建或重放未知副作用。
6. **用户控制**：运行/交接/下一轮待启动时暂停；恢复后仍暂停；等待审批不得自动续跑；交接期间用户输入有确定归属和顺序。
7. **终点与无进展**：完成后不再轮换；反复失败、超时、step限制、成本/轮次上限有界停止，区分阻塞和完成。
8. **普通功能回归**：普通聊天、压缩、move、fork、执行claim恢复和权限规则不因新任务模式改义。
9. **界面验收**：一个任务持续可见，轮次可查；估算与实测不混淆；停止控件不只停止当前会话。

优先使用确定性预算/状态测试与临时项目，不在常规CI中请求真实Midea或连接工业设备。真实接口预算与连续运行的证据另行记录。
